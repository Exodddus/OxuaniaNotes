# Lec14 Transaction

## 1. Transaction 概念

- **事务（transaction）** 是一个程序执行单元，它会访问并且可能更新多个数据项。
- 典型目标：让一组操作作为一个逻辑整体执行，要么全部成功，要么全部失败。

转账例子：从账户 `A` 向账户 `B` 转 `50` 元。

```sql
update account
set balance = balance - 50
where account_number = A;

update account
set balance = balance + 50
where account_number = B;

commit;
```

也可以抽象成低层操作：

1. `read(A)`
2. `A := A - 50`
3. `write(A)`
4. `read(B)`
5. `B := B + 50`
6. `write(B)`

事务处理主要解决两类问题：

- **Failure**：硬件故障、软件错误、系统崩溃等。
- **Concurrent execution**：多个事务并发执行时可能互相干扰。

## 2. ACID 性质

### 2.1 Atomicity

- 原子性：事务中的操作要么全部反映到数据库中，要么一个都不反映。
- 对上面的转账例子，如果执行完 `write(A)` 后系统崩溃，而 `write(B)` 还没执行，那么钱会“丢失”，数据库会进入不一致状态。
- 因此系统必须保证：**部分执行的事务，其更新不能永久留在数据库中**。

### 2.2 Consistency

- 一致性：事务在**隔离执行**时，必须把数据库从一个一致状态带到另一个一致状态。
- 对转账例子来说，一个核心约束是账户总额不变，即执行前后都应满足 `$A + B$` 不变。
- 更一般地，一致性还包括各种完整性约束，例如：
  - 所有账户余额之和减去贷款总额应等于库存现金；
  - 主键、外键、检查约束等必须继续成立。
- 注意：事务执行过程中数据库可以**暂时不一致**；但事务成功提交后必须恢复到一致状态。
- 如果事务逻辑本身写错了，即使有并发控制和恢复机制，也仍然可能破坏一致性。

### 2.3 Isolation

- 隔离性：虽然多个事务可以并发执行，但每个事务都不应看到其他并发事务的中间结果。
- 可以理解成：对于任意两个事务 $T_i$ 和 $T_j$，在 $T_i$ 看来，要么 $T_j$ 在它开始前已经完成，要么 $T_j$ 在它结束后才开始。
- 仍以转账为例：若事务 `T1` 在执行完 `write(A)` 但还没执行 `write(B)` 时，另一个事务 `T2` 去读取 `A` 和 `B`，就会看到错误的总和，即看到 $A + B$ 变小。
- 最简单的隔离办法是**串行执行**，但这会牺牲性能。

### 2.4 Durability

- 持久性：一旦系统通知用户事务已经成功完成，那么该事务对数据库的修改就必须永久保存。
- 即使随后发生系统崩溃，这些修改也不能丢失。

## 3. 简单事务模型

事务通过两类基本操作访问数据：

- `read(X)`：把数据库中的数据项 `X` 读到事务在主存中的工作区变量。
- `write(X)`：把事务工作区中变量 `X` 的值写回数据库中的数据项 `X`。

可以把事务理解成：**先读到本地工作区，计算后再写回数据库**。

---

## 4. 事务状态

一个事务通常处于以下几种状态之一：

- **Active**：初始状态，事务正在执行。
- **Partially committed**：最后一条语句已经执行完，但结果还没有最终持久化。
- **Failed**：系统发现事务无法继续正常执行。
- **Aborted**：事务已经回滚，数据库恢复到该事务开始前的状态。
- **Committed**：事务成功完成。

`Aborted` 之后通常有两种处理方式：

- 重启该事务；
- 直接终止该事务。

常见状态流转可以写成：

- 正常路径：`Active -> Partially committed -> Committed`
- 失败路径：`Active -> Failed -> Aborted`

---

## 5. 并发执行的意义

数据库允许多个事务并发执行，主要优点有：

- 提高 CPU 和磁盘利用率；
- 提高系统吞吐量；
- 缩短平均响应时间，短事务不必一直排在长事务后面。

例如：一个事务在等待磁盘 I/O 时，另一个事务可以使用 CPU。

---

## 6. 并发异常

课件列出了几类典型异常：

- **Lost Update**：两个事务都修改同一数据项，后写入的结果覆盖先前结果，导致某次更新丢失。
- **Dirty Read**：一个事务读到了另一个事务尚未提交的数据；如果对方随后回滚，当前事务读到的就是“脏”数据。
- **Unrepeatable Read**：同一事务中两次读取同一记录，结果不同，因为中间有其他事务提交了更新。
- **Phantom Problem**：同一事务中两次执行条件查询，第二次多出或少了若干行，因为其他事务插入或删除了满足条件的元组。

这些异常本质上都说明：**并发调度如果控制不好，就会破坏隔离性，进而影响一致性**。

---

## 7. Schedule（调度）

- **调度（schedule）** 是并发事务中各条指令的时间顺序。
- 一个调度必须：
  - 包含所有事务的全部指令；
  - 保持每个事务内部原有的指令顺序。
- 成功完成的事务最后有 `commit`；
- 失败的事务最后有 `abort`。

### 7.1 串行调度

- **串行调度（serial schedule）**：一个事务完整执行完后，另一个事务才开始。
- 串行调度最容易保证正确性，因为事务之间没有交叉。

例子：

- 先执行 `T1`，再执行 `T2`；
- 或先执行 `T2`，再执行 `T1`。

只要每个事务本身保持一致性，那么串行执行通常也能保持数据库一致性。

---

## 8. Serializability（可串行化）

- 因为串行执行太慢，我们希望允许并发。
- 核心问题变成：**一个并发调度是否“等价于”某个串行调度？**
- 如果答案是是的，这个并发调度就是 **serializable**。

课件提到两种主要形式：

- **Conflict serializability**
- **View serializability**

### 8.1 Conflict serializability

如果一个调度能通过一系列**不冲突指令的交换**，变换成某个串行调度，那么该调度就是 **conflict serializable**。

#### 冲突指令

设事务 `$T_i$` 和 `$T_j$` 分别包含指令 `$l_i$` 和 `$l_j$`。若二者访问同一数据项 `Q`，且至少一个是写操作，则二者冲突。

四种常见情况：

- `read(Q)` 与 `read(Q)`：**不冲突**
- `read(Q)` 与 `write(Q)`：**冲突**
- `write(Q)` 与 `read(Q)`：**冲突**
- `write(Q)` 与 `write(Q)`：**冲突**

直观理解：冲突意味着这两个操作之间存在逻辑上的先后约束，不能任意交换。

### 8.2 前驱图 / 优先图（precedence graph）

判断冲突可串行化的经典方法是构造前驱图：

- 顶点：各个事务 $T_1, T_2, \dots, T_n$
- 有向边 $T_i \to T_j$：表示 `T_i` 与 `T_j` 存在冲突，且 `T_i` 的相关操作先于 `T_j`

结论：

- 调度 **conflict serializable** 当且仅当前驱图 **无环**。
- 如果图无环，则可以对图做**拓扑排序**，得到一个等价的串行顺序。

### 8.3 View serializability

如果两个调度满足以下条件，则它们 **view equivalent**：

- 对每个数据项 `Q`，若某事务在一个调度中读到 `Q` 的初值，那么在另一个调度中也必须读到 `Q` 的初值；
- 若某事务在一个调度中读到的是另一事务写出的 `Q`，那么在另一个调度中也必须读到同一个写操作产生的值；
- 对每个数据项 `Q`，最终执行 `write(Q)` 的事务必须相同。

定义：

- 若某个调度与某个串行调度 view equivalent，则该调度是 **view serializable**。

关系：

- 每个 conflict-serializable 调度一定也是 view-serializable；
- 反过来不一定成立。

## 9. Recoverability（可恢复性）

### 9.1 Recoverable schedule

若事务 `Tj` 读到了事务 `Ti` 写出的数据，那么必须满足：

- `Ti` 的 `commit` 先于 `Tj` 的 `commit`

否则，如果 `Tj` 先提交，而 `Ti` 之后回滚，那么 `Tj` 就基于错误数据做出了不可撤销的结果，这种调度不可恢复。

### 9.2 Cascading rollback

- **级联回滚**：一个事务失败，导致一串依赖它读值的事务都必须回滚。
- 根本原因是：后续事务读到了尚未提交的数据。

### 9.3 Cascadeless schedule

若事务 `Tj` 读到了 `Ti` 写过的数据，则要求：

- `Ti` 的 `commit` 必须先于 `Tj` 的 `read`

这样一来：

- 不会发生级联回滚；
- 每个 cascadeless schedule 都一定是 recoverable。

实际中我们通常更希望调度至少满足：

- 可恢复；
- 最好还是无级联回滚。

---

## 10. 并发控制目标

数据库需要提供并发控制机制，使产生的调度尽量满足：

- 是 conflict serializable 或 view serializable；
- 是 recoverable；
- 最好还是 cascadeless。

注意：如果等调度执行完再检查是否可串行化，就已经太晚了。所以数据库系统通常使用协议在执行过程中直接约束调度。

课件提到的几类并发控制协议：

- **Lock-based protocols**
  - 锁整个数据库还是锁单个数据项；
  - 锁持有多久；
  - 共享锁（shared）和排他锁（exclusive）如何配合。
- **Timestamp-based protocols**
  - 事务开始时分配时间戳；
  - 数据项维护读时间戳和写时间戳；
  - 用时间戳判断访问顺序是否合法。
- **Validation-based protocols**
  - 又称乐观并发控制；
  - 适合冲突较少的场景；
  - 事务通常经历读、验证、写三个阶段。

## 11. 弱一致性与隔离级别

有些应用愿意用较弱的一致性换更高性能，例如：

- 只读事务做“近似统计”；
- 查询优化器收集近似统计信息。

因此 SQL 标准提供了不同隔离级别。

### 11.1 Serializable

- 只能读已提交数据；
- 对同一记录重复读取必须得到相同结果；
- 目标是效果上等价于串行执行，是最强隔离级别。

### Repeatable read

- 只读已提交的数据，且对同一记录的重复读取必须返回相同的结果。

### 11.2 Read committed

- 只能读已提交数据；
- 但同一事务两次读同一记录，结果可能不同。

### 11.3 Read uncommitted

- 甚至允许读取未提交数据；
- 可能出现 dirty read。

### 课件中的提醒

- 有些数据库默认并不提供真正的 serializable 调度；
- 课件举例提到 Oracle、PostgreSQL 默认支持的是 `snapshot isolation`，它不属于 SQL 标准中的经典四级定义。

## 12. SQL 中的事务定义

- 在 SQL 中，事务通常是**隐式开始**的。
- 一个事务的结束方式：
  - `COMMIT WORK`：提交当前事务，并开始一个新事务；
  - `ROLLBACK WORK`：回滚当前事务。

很多数据库默认行为：

- 每条 SQL 语句如果成功执行，会被**隐式提交**。

这个行为通常可以关闭，例如在 JDBC 中：

```java
connection.setAutoCommit(false);
```

事务隔离级别可以：

- 在数据库级别设置；
- 在事务开始时调整。

例如：

```sql
set transaction isolation level serializable;
```

JDBC 示例：

```java
connection.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
```

## 13. 记忆主线

可以用下面这条主线记整章：

- **为什么需要事务**：故障 + 并发会破坏正确性。
- **事务想保证什么**：ACID。
- **并发为什么麻烦**：会出现丢失修改、脏读、不可重复读、幻读等异常。
- **如何判断并发是否正确**：看是否可串行化、是否可恢复。
- **数据库如何落地**：并发控制协议 + 隔离级别 + `COMMIT/ROLLBACK`。

---

## 14. 这章最重要的几个句子

- 事务是数据库中的**逻辑工作单元**。
- 原子性保证“**要么全做，要么全不做**”。
- 一致性要求事务把数据库从一个一致状态带到另一个一致状态。
- 隔离性要求并发执行看起来像串行执行。
- 持久性要求一旦提交成功，结果永久生效。
- **可串行化**解决“并发执行是否正确”。
- **可恢复性**解决“读取他人结果后，提交顺序是否安全”。
