# Chap 3-1: Instruction-Level Parallelism — Static Parallelism

***"本章核心"***

- **ILP 与流水线**：流水线通过重叠多条指令的不同阶段提高吞吐率，但不会缩短单条指令的延迟。
- **浮点流水线**：区分操作延迟（latency）和启动间隔（initiation interval），理解多功能单元、非流水化除法器及乱序完成带来的新冒险。
- **依赖与冒险**：数据依赖、名称依赖、控制依赖分别约束可重排范围；RAW 是真依赖，WAR/WAW 是名称依赖。
- **静态调度**：编译器在保持异常行为和数据流的前提下重排指令，以填充流水线空隙。
- **循环展开**：减少循环控制开销，并暴露不同迭代之间的 ILP；必须配合寄存器重命名和调度才能充分提速。
- **跨基本块调度**：trace scheduling 聚焦高频路径，superblock 用单入口结构减少补偿代码的复杂度。
- **控制冒险**：冻结/冲刷、静态预测不跳转、静态预测跳转和延迟分支；流水线越深，预测准确率越重要。

## Instruction-Level Parallelism

**指令级并行**（instruction-level parallelism, **ILP**）是指在一段指令流中重叠或同时执行多条指令。利用 ILP 的方法分为两类：

- **静态并行**：由编译器在编译时分析依赖、重排代码；适合结构规则、数据级并行明显的程序。
- **动态并行**：由硬件在运行时发现并行性，后续动态调度部分讨论。

### Pipelining

**流水线**（pipelining）把一项任务分成多个阶段，并在不同资源上重叠执行多项任务。它的本质是：前一条指令尚未完成时，后一条指令已经开始执行。

课件中的洗衣例子包含洗涤 30 分钟、烘干 40 分钟、折叠 20 分钟三个阶段。四批衣物顺序执行需要：

$$
4\times(30+40+20)=360\ \text{min}=6\ \text{h}
$$

流水执行时，第一批仍需 90 分钟，但后续任务受到最慢阶段（40 分钟）的限制，总时间为：

$$
30+4\times40+20=210\ \text{min}=3.5\ \text{h}
$$

因此流水线的直接收益是**提高吞吐率**，而不是缩短单个任务的延迟。四批衣物的平均完成时间降为 $210/4=52.5$ 分钟，但第一批仍需 90 分钟。

对于理想的 $k$ 级均衡流水线，若忽略流水寄存器开销和冒险：

$$
T_{\text{pipe per instr}}=\frac{T_{\text{non-pipe per instr}}}{k},
\qquad
\text{Speedup}_{\max}=k
$$

实际流水线并不完全均衡，时钟周期由最慢阶段决定，还会受到流水寄存器开销、结构冒险、数据冒险和控制冒险的影响。

### Integer Pipeline and Forwarding

经典 RISC-V 五级流水线为：

| 阶段 | 含义 |
|---|---|
| IF | 取指令 |
| ID | 译码并读取寄存器 |
| EX | 执行运算或计算地址 |
| MEM | 访问数据存储器 |
| WB | 写回寄存器 |

相邻指令存在 RAW 依赖时，冒险检测逻辑比较前面指令的目的寄存器与后续指令的源寄存器。若结果已经产生但尚未写回，可通过 **forwarding/bypassing** 直接前递；若结果尚未产生，例如紧随 load 的使用者，则仍需停顿。

## Floating-Point Pipeline

浮点运算比整数运算复杂。若强行让浮点运算在一个时钟周期内完成，要么拉长整个处理器时钟周期、拖慢整数指令，要么使用面积和成本很高的组合逻辑。因此处理器通常采用：

- 允许浮点运算在 EX 部分经历多个周期；
- 设置独立的浮点加法器、乘法器和除法器；
- 尽可能将功能单元流水化，使多条独立运算能够重叠。

### Latency and Initiation Interval

- **延迟**（latency）：产生结果的指令与使用该结果的指令之间必须间隔的周期数。
- **启动间隔**（initiation/repeat interval）：同一功能单元连续启动两次同类操作之间至少相隔的周期数。

二者不能混淆：一个运算可以需要很多周期才产生结果，但若功能单元充分流水化，仍可每周期启动一个新运算。

课件采用的参数如下：

| 功能单元 | Latency | Initiation interval |
|---|---:|---:|
| Integer ALU | 0 | 1 |
| Data memory（整数/浮点加载） | 1 | 1 |
| FP add | 3 | 1 |
| FP multiply（也用于整数乘法） | 6 | 1 |
| FP divide（也用于整数除法） | 24 | 25 |

对于充分流水化的执行单元：

$$
\text{latency}=\text{从 EX 到结果产生阶段的级数}-1
$$

例如 FP add 经过 `A1-A4`，延迟为 3；FP multiply 经过 `M1-M7`，延迟为 6。除法器不完全流水化，因此延迟为 24，下一条除法要到 25 个周期后才能启动。

### Generalized FP Pipeline

通用浮点流水线在 `IF-ID` 和 `MEM-WB` 之间并列放置多条执行路径：

- 整数/地址计算单元：`EX`；
- 浮点加法器：`A1-A4`；
- 浮点/整数乘法器：`M1-M7`；
- 浮点/整数除法器：多周期 `DIV`，且不完全流水化。

不同指令需要数据和产生结果的时刻也不同：浮点运算在执行路径入口读取操作数，在末级产生结果；load 在 EX 计算地址、MEM 得到数据；store 在 EX 需要地址，在 MEM 才需要待写数据。调度和前递必须按照这些实际时刻判断，而不能只看指令是否相邻。

### Hazards in FP Pipelines

多周期、不同长度的执行路径会引入经典五级整数流水线中不明显的问题。

#### Structural Hazards

- 非流水化除法器尚忙时，下一条除法不能发射。
- 不同延迟的指令可能在同一周期同时到达 WB，争用寄存器写端口。

写端口冲突可在 ID 阶段用移位寄存器预订未来的写回周期，提前阻塞冲突指令；也可等指令到达 MEM/WB 时再仲裁，但控制更复杂。若必须选择，通常优先保证延迟更长、已经执行更久的指令。

#### Data Hazards and Out-of-Order Completion

- **RAW**：长延迟操作使使用者等待更久，因而更常见。
- **WAW**：后发射的短指令可能先写回同一寄存器，破坏程序顺序。可延迟后者发射，或禁止较早长指令最终写回，以确保最后一次写入与程序顺序一致。
- **WAR**：在本课件的顺序发射、ID 读操作数模型中通常不会出现，因为早指令已先读取源操作数。

当后发射的短指令先于早发射的长指令完成时，就发生**乱序完成**（out-of-order completion）。它会使异常处理变得不精确：发生异常时，后面的指令可能已经修改了可见状态。

可选处理思路包括：

1. 简化实现，接受不精确异常；
2. 缓冲结果，等待所有更早指令完成后再提交；
3. 记录流水线中指令及其 PC，供陷阱处理程序恢复；
4. 仅在确定所有更早指令都不会异常时才发射新指令。

### Hazard Detection and Forwarding

顺序发射的浮点流水线可在 ID 阶段依次检查：

1. **结构冒险**：目标功能单元是否可用，未来写回端口是否已被占用；
2. **RAW**：源寄存器是否仍是某条已发射指令的待写目的寄存器；
3. **WAW**：是否已有未完成指令将写入相同目的寄存器，并判断二者完成次序。

前递网络也必须扩展，可能从 `EX/MEM`、`A4/MEM`、`M7/MEM`、`DIV/MEM`、`MEM/WB` 等位置把结果送到浮点指令的输入端。

## MIPS R4000: A Superpipelined Example

MIPS R4000 将经典五级流水线细分为八级，以缩短关键路径、提高时钟频率。这种进一步切分流水级的设计称为**超流水线**（superpipelining）。

| 阶段 | 主要工作 |
|---|---|
| IF | 选择 PC，开始访问指令缓存 |
| IS | 完成指令缓存访问 |
| RF | 译码、读寄存器、冒险检测、检查 I-cache 命中 |
| EX | ALU、有效地址、分支目标和条件计算 |
| DF | 数据缓存访问的前半段 |
| DS | 完成数据缓存访问 |
| TC | 标签检查，确定 D-cache 是否命中 |
| WB | load 和寄存器运算写回 |

其关键特征包括：

- load-use 延迟为 2 个周期；
- 分支在 EX 才确定结果。对默认“不跳转”取指而言，不跳转分支有 1 个延迟槽，而跳转分支约有 3 个周期的代价；
- 前递路径从 ALU/MEM 或 MEM/WB 延伸到 `EX/DF`、`DF/DS`、`DS/TC`、`TC/WB` 等位置；
- 浮点部分包含加法、乘法、除法三个功能单元，执行时间随操作不同可从数周期到上百周期。

这个例子说明：流水线切得越深，时钟可以越快，但 load、分支、长延迟运算和异常处理也会更复杂。

## Dependences and Hazards

若两条指令在资源充足的任意深流水线中同时执行而不会引起停顿，则它们是**并行指令**。若必须保持先后顺序，则它们存在依赖；依赖指令仍可能部分重叠，只是不能任意重排。

### Data Dependence

若指令 $i$ 产生的结果可能被指令 $j$ 使用，或存在从 $i$ 到 $j$ 的传递依赖链，则称 $j$ **数据依赖**于 $i$。例如：

```asm
Loop:
    fld     f0, 0(x1)
    fadd.d  f4, f0, f2
    fsd     f4, 0(x1)
    addi    x1, x1, -8
    bne     x1, x2, Loop
```

其中 `fld -> fadd.d`、`fadd.d -> fsd`、`addi -> bne` 都是写后读的数据依赖。数据依赖是程序语义中的**真依赖**，通常只能通过调度隐藏等待时间，不能靠简单重命名消除。

### Name Dependence

两条指令使用相同寄存器或内存位置，但该名称上没有真实数据流时，存在**名称依赖**（name dependence）：

- **反依赖**（antidependence）：先读后写，对应 WAR；
- **输出依赖**（output dependence）：先写后写，对应 WAW。

名称依赖不是真实的数据传递，可以通过**寄存器重命名**消除。重命名既可由编译器静态完成，也可由硬件动态完成。

### Data Hazards

依赖不一定立即形成冒险。只有当相关指令足够接近，而且重叠执行会改变操作数访问顺序时，才产生数据冒险。

| 冒险 | 含义 | 对应依赖 | 错误结果 |
|---|---|---|---|
| RAW | Read After Write | 真数据依赖 | 后指令读到旧值 |
| WAR | Write After Read | 反依赖 | 前指令读到新值 |
| WAW | Write After Write | 输出依赖 | 最终保留了错误写入 |

`RAR` 只有共同读取，没有状态冲突，不是冒险。

### Control Dependence

```c
if (p1) S1;
if (p2) S2;
```

`S1` 控制依赖于 `p1`，`S2` 控制依赖于 `p2`。控制依赖限制指令能否跨越分支移动，但优化真正需要保持的是：

- **异常行为**（exception behavior）：重排不能改变异常的产生方式；较宽松的要求是不引入原程序不会产生的新异常。
- **数据流**（data flow）：每个使用者必须得到原程序路径上正确生产者的值。

例如：

```asm
add  x2, x3, x4
beq  x2, x0, L1
ld   x1, 0(x2)
L1:
```

不能随意把 `ld` 移到分支前，否则原本跳转时不会执行的访存可能产生地址或保护异常。

又如：

```asm
add  x1, x2, x3
beq  x4, x0, L
sub  x1, x5, x6
L:
or   x7, x1, x8
```

`or` 读取的 `x1` 可能来自 `add` 或 `sub`，由分支结果决定。优化必须保留这种动态数据流。

### Pipeline CPI

流水线 CPI 可以分解为：

$$
\text{Pipeline CPI}
=\text{Ideal CPI}
+\text{Structural stalls}
+\text{Data-hazard stalls}
+\text{Control stalls}
$$

静态调度的目标是在不破坏依赖、异常行为和数据流的前提下，通过指令重排降低后三类停顿。

## Static Scheduling

### Pipeline Scheduling

考虑：

```c
for (i = 999; i >= 0; --i)
    x[i] = x[i] + s;
```

未调度的 RISC-V 循环为：

```asm
Loop:
    fld     f0, 0(x1)
    # 1-cycle stall: load-use
    fadd.d  f4, f0, f2
    # 2-cycle stall: wait for FP add
    fsd     f4, 0(x1)
    addi    x1, x1, -8
    bne     x1, x2, Loop
```

每次迭代执行 5 条指令并停顿 3 周期，共需：

$$
5+1+2=8\ \text{cycles/element}
$$

把独立的指针更新提前，可以填掉 load-use 的一个空隙。由于 `x1` 已先减 8，store 偏移要从 `0(x1)` 改为 `8(x1)`：

```asm
Loop:
    fld     f0, 0(x1)
    addi    x1, x1, -8
    fadd.d  f4, f0, f2
    # 2-cycle stall
    fsd     f4, 8(x1)
    bne     x1, x2, Loop
```

调度后每个元素需 7 周期，但真正完成数组计算的只有 `fld`、`fadd.d`、`fsd` 三条，即有效工作仅占 $3/7$。要继续减少停顿和循环控制开销，需要同时观察多个迭代。

### Loop Unrolling

**循环展开**（loop unrolling）复制多份循环体，并合并指针更新、循环判断和分支，从而：

- 摊薄 `addi`、`bne` 等循环开销；
- 暴露不同迭代之间的独立指令，为调度提供更大窗口；
- 用不同寄存器重命名各迭代的临时值，消除不必要的 WAR/WAW；
- 让现代超标量或乱序处理器也更容易发现并行性。

将循环展开四次但暂不跨迭代调度：

```asm
Loop:
    fld     f0,   0(x1)
    fadd.d  f4,   f0,  f2
    fsd     f4,   0(x1)

    fld     f6,  -8(x1)
    fadd.d  f8,   f6,  f2
    fsd     f8,  -8(x1)

    fld     f10, -16(x1)
    fadd.d  f12,  f10, f2
    fsd     f12, -16(x1)

    fld     f14, -24(x1)
    fadd.d  f16,  f14, f2
    fsd     f16, -24(x1)

    addi    x1, x1, -32
    bne     x1, x2, Loop
```

控制指令虽然由每元素 2 条降为四个元素共享 2 条，但每组 load-add-store 之间仍有 3 个停顿周期：

$$
\frac{12\ \text{data instr}+2\ \text{control instr}+12\ \text{stall}}{4}
=\frac{26}{4}=6.5\ \text{cycles/element}
$$

将四次加载、四次加法、四次存储分组调度后，独立指令恰好填入延迟空隙：

```asm
Loop:
    fld     f0,   0(x1)
    fld     f6,  -8(x1)
    fld     f10, -16(x1)
    fld     f14, -24(x1)

    fadd.d  f4,   f0,  f2
    fadd.d  f8,   f6,  f2
    fadd.d  f12,  f10, f2
    fadd.d  f16,  f14, f2

    fsd     f4,   0(x1)
    fsd     f8,  -8(x1)
    fsd     f12, -16(x1)
    fsd     f16, -24(x1)

    addi    x1, x1, -32
    bne     x1, x2, Loop
```

此时四个元素只需 14 周期：

$$
\frac{14}{4}=3.5\ \text{cycles/element}
$$

相对未调度原循环的加速比为：

$$
\text{Speedup}=\frac{8}{3.5}\approx2.29
$$

#### Correctness and Limits

循环展开与调度必须完成以下工作：

1. 证明不同迭代相互独立，特别是不同 load/store 地址不会别名到同一位置；
2. 为各迭代分配不同临时寄存器；
3. 删除多余的指针更新和分支，并修正偏移与终止条件；
4. 在重排后保留所有真依赖、异常行为和数据流。

若循环次数 $n$ 不是展开因子 $k$ 的整数倍，通常生成：

- 一个执行 $n\bmod k$ 次的清理循环；
- 一个执行 $\lfloor n/k\rfloor$ 次的 $k$ 路展开循环。

展开因子也并非越大越好，其限制包括代码规模增长、指令缓存压力、活跃值增多造成的**寄存器压力**，以及编译器难以证明的内存别名。

## Scheduling Across Branches

循环展开主要扩大单个循环体。要跨越多个基本块获得更大的调度范围，还需处理控制流。现实程序的分支通常并不均匀：一条路径可能有 99% 的执行概率，另一条只有 1%。静态调度可以先优化高频路径，再保证低频路径仍然正确。

### Trace Scheduling

**Trace** 是控制流图中一条很可能连续执行的基本块序列。Trace scheduling 包括：

1. **Trace selection**：根据剖析信息或静态启发式选择高频路径；
2. **Trace compaction**：把路径上的操作跨基本块重排、压缩到更少或更宽的指令中。

若控制流从 trace 中途离开，称为 **trace exit**；从其他路径跳入 trace 中部，称为 **trace entrance**。跨分支移动的指令可能在这些入口/出口上少执行或多执行，因此编译器需复制 **fixup/compensation code** 修复低频路径。

Trace 入口和出口过多时，补偿代码会迅速复杂化并增加代码规模。

### Superblock

**Superblock** 是**单入口、多出口**的基本块序列。编译器通常通过复制存在侧入口的基本块（tail duplication）消除 trace 中部入口，然后在 superblock 内沿高频路径调度。

单入口结构的好处是：无需处理从中途闯入、绕过已提前执行指令的情况；仍可从多个出口离开，并在出口处安排必要的补偿代码。代价依然是代码复制和体积增长。

## Control Hazards and Static Branch Handling

分支或跳转可能把下一 PC 从 `PC+4` 改为目标地址。若结果到 ID 末尾甚至更晚才确定，取指阶段就不知道下一条该取哪条指令。等待或重取本质上都是流水线停顿；课件指出每个分支增加一个停顿周期就可能造成约 10%-30% 的性能损失。

### Four Simple Schemes

#### 1. Freeze or Flush

在分支目标和方向确定前冻结流水线，或把已经进入流水线的错误路径指令冲刷为 `nop`。实现简单，但无论分支实际跳不跳都付出固定代价。

#### 2. Predict Not Taken

始终预测分支**不跳转**，继续从 `PC+4` 取指：

- 实际不跳转：流水线无额外损失；
- 实际跳转：把错误取入的指令变为 `nop`，从目标地址重新取指。

#### 3. Predict Taken

始终预测分支**跳转**。只有在**目标地址早于分支方向得到确定**时，这种方案才有意义；若目标地址也要等到分支条件算完才知道，就无法提前从目标取指。

#### 4. Delayed Branch

把分支后的一个或多个位置定义为**分支延迟槽**（branch delay slot）。延迟槽中的指令无论分支是否跳转都会执行，因此编译器应放入与分支结果无关的有用指令；找不到时只能填 `nop`。

延迟槽可尝试从分支前、目标路径或顺序后继中选择指令，但必须保证两条路径的语义和异常行为都正确。随着流水线加深，需要的延迟槽增多，静态填充越来越困难，因此现代高性能处理器更依赖动态预测和推测。

### Prediction Accuracy and Pipeline Depth

若理想 CPI 为 1、分支比例为 $f_b$、预测准确率为 $a$、误预测代价为 $P$，可估算：

$$
\text{CPI}=1+f_b(1-a)P
$$

课件例 1：20 级流水线，每 5 条指令有 1 条分支，取 500 条指令，共有 100 个分支；每次误预测按 20 周期计算。

| 准确率 | 误预测数 | 总周期 |
|---:|---:|---:|
| 100% | 0 | $500$ |
| 99% | 1 | $500+20\times1=520$ |
| 90% | 10 | $500+20\times10=700$ |

课件例 2：分支比例为 20%，若分支分别在第 3 级和第 10 级确定，则误预测代价分别近似为 2 和 9 个周期。

| 准确率 | 第 3 级确定 | 第 10 级确定 |
|---:|---:|---:|
| 50% | $1+0.2\times0.5\times2=1.20$ | $1+0.2\times0.5\times9=1.90$ |
| 90% | $1+0.2\times0.1\times2=1.04$ | $1+0.2\times0.1\times9=1.18$ |

结论很直接：**分支确定得越晚、流水线越深，提高预测准确率带来的收益越大。**

### BTB and Direction Predictor

课件最后用动态硬件作为下一部分的引子：取指阶段同时查询

- **方向预测器**（direction predictor）：预测 taken/not taken；
- **分支目标缓冲器**（branch target buffer, **BTB**）：缓存分支 PC 对应的目标地址。

若 BTB 命中且方向预测为 taken，下一次从缓存的目标地址取指；否则使用 `PC+4`。预测错误时再恢复正确 PC，并冲刷错误路径指令。

## Review

- 流水线提高多条指令的吞吐率，不等于降低单条指令延迟。
- 多周期浮点单元要同时考虑 latency、initiation interval、写回端口和乱序完成。
- 数据依赖是真实数据流；WAR/WAW 属于可通过重命名消除的名称依赖。
- 静态调度通过独立指令填空隙；循环展开负责暴露更多独立指令，两者配合效果最好。
- Trace scheduling 和 superblock 把调度范围扩展到多个基本块，但要用补偿代码维持低频路径正确。
- 深流水线放大控制冒险代价，因此分支预测准确率会显著影响 CPI。
